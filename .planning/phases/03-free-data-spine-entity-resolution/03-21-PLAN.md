<objective>
Apply the phase's four migrations to production behind a human gate, deploy, and prove the four
screens on the real URL.

Purpose: 🔴 **Production migration is a human checkpoint, never automatic.** `pnpm db:migrate:prod`
is the only path and `scripts/db.ts` demands the session pooler on port 5432. This plan opens the
gate, runs it once, seeds the new reference rows, deploys, and then runs the e2e suite against
the deployed app.

🔴 **The `preset-detail.spec.ts` two-databases trap decides the e2e scope.** `withDb()` opens
`TEST_DATABASE_URL` — always the **local** `siteless_test` — while `tenantId()` reads the org id
out of the app that `E2E_BASE_URL` points at. Against a deployed URL those are two different
databases. Phase 3's ingest is a desk script, so `/review` and `/businesses/[id]` cannot be seeded
*through the product* at all. The decided scope, stated here rather than left to a spec that
quietly self-skips forever:

| Screen | e2e | Why |
|---|---|---|
| `/sources` | ✅ chrome only — nav, the four static rows, headings, the attribution block | Executor Rule 27 makes those rows static structure, so they render with no data |
| `/businesses` | ✅ chrome only — nav, the search field, the filters, the empty state | The field and filters render immediately by design |
| `/review` | ❌ DB tests only in this phase | Needs seeded candidate pairs the deployed database will not have |
| `/businesses/[id]` | ❌ DB tests only in this phase | Same |
| `touch-targets` | ✅ extended in 03-04, run here | The nav change must be proven on the real app |

Output: two new specs, the owed `presets.spec.ts` teardown, a production migration, a deploy.
</objective>
