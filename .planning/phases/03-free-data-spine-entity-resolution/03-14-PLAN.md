<objective>
Ship the resolve pass as a desk script: block → score → auto-merge → enqueue review, with the
block-size cap and a persisted run report.

Purpose: DEDUP-01 and DEDUP-02's execution half. **Blocking is a materialised pass, never a live
query** — candidate generation takes ~2 minutes at RGV scale, runs once per pass, and writes
`merge_candidates`. The app never issues a blocking query: `/review` reads
`merge_candidates where decision='pending' order by … limit 1`, which is one indexed row.

🔴 **Pairwise auto-merge must be cluster-aware.** Measured: one Comptroller row
(`RIO STONE PRODUCTS, INC.`) matches **two** Overture rows at similarity 1.000. Process
candidates in descending score and resolve both sides through `coalesce(merged_into_id, id)`
before each merge; without that re-point the second merge writes a `merged_into_id` pointing at
an already-merged loser and the chain breaks. Mutation **M25**.

Expected shape of a real pass, from the measurements: **29,701** candidate pairs from the union
of the three blocks (B1 12,717 ∪ B2′ 14,357 ∪ B3 ≤5/left-row), against 1.99 billion all-pairs.

Output: `scripts/resolve.ts`, a `pnpm` script entry, the end-to-end DB test.
</objective>

🔴 **Without `resolveEtlOrg` this whole pass raises `42501` on its first auto-merge.**
`app.record_merge` (03-11) and `app.emit_event` (`drizzle/0011`) both open with
`v_org := app.current_org_id()` and raise `42501` when it is null, and `app.current_org_id()`
(`drizzle/0002_tenancy_functions.sql` line 5) resolves the org from `request.jwt.claims` and from
nothing else. This script connects as the owner and sets no Clerk claims, so `resolveEtlOrg` is
what installs the org claim — transaction-LOCAL, carrying `{o:{id}}` only, deliberately without
`sub` so the merge is still attributed `etl:resolve` (03-09, T-3-15). The stage loops and the
per-candidate merge loop each open their own transaction; every one of them calls both helpers.

🔴 **Stage 0 — preflight, before stage 1 does any work.** In a throwaway transaction, call
`setEtlActor` + `resolveEtlOrg`, then
`select app.current_org_id()` and assert it is non-null and equals the resolved org id. Abort with
a named error naming `--org` if it is not. The stages that follow take ~2 minutes and the merge
loop writes; failing at second zero on a missing org beats failing after the blocker has run.

**Stage 1 — chain detection.** Run `chainDetectionSql` **before** the blocker, so a flagged row
is already flagged when it is scored. Record the flagged-name and flagged-row counts in `stats`
(expect ~1,025 names / 9,782 rows Overture, ~444 / 2,091 Comptroller).

**Stage 2 — block.** Inside one transaction per shape, each beginning with
`set local pg_trgm.similarity_threshold = <BLOCK_SIMILARITY_THRESHOLD>`:
B1 (phone, `phone_blockable = true`), then B2′ (`(postal, street_num)` gated at similarity ≥ 0.3),
then B3 (the GIN lateral top-5 within `postal`). Each writes `merge_candidates` with
`on conflict (org_id, left_id, right_id) do nothing`, so the union is free.
🔴 A block whose pair count would exceed `MAX_BLOCK_PAIRS` (500) is **skipped and named** in
`stats.skipped_blocks` as `{ block_key, size }`. A silently truncated block is how a whole mall
disappears from the spine.

**Stage 3 — the 25 km hard rule.** Run `distanceGateSql` immediately after blocking, so pairs
over 25 km are `distinct` **before** anything is scored (measured 303 ms over 332,738 pairs).

**Stage 4 — score.** Read every `decision='pending'` candidate with both sides' `Side` columns
**and `similarity(a.name_norm, b.name_norm) as name_sim` computed in SQL** — 🔴 the scorer never
recomputes trigram similarity in TypeScript; pg_trgm's trigram set is not reproducible there and
a blocker and a scorer that disagree about a key produce candidates that vanish when re-scored.
Call `score(pair)` from the one committed module and write back `score` and `features`.

**Stage 5 — auto-merge.** Select `decision='pending' and score >= 95` **ordered by score
desc, id asc** (`id asc` makes a re-run deterministic). For each:

- skip when `chain_key` is set on either side — D-11: auto-merge skips flagged rows, and the
  review queue shows the flag when a flagged row lands there via another signal
- skip when the pair already has `decision='distinct'` (an unmerge wrote that, D-20 / M21)
- 🔴 re-point **both** sides through `coalesce(merged_into_id, id)` and re-read them; if the two
  resolve to the same business, mark the candidate `merged` and continue
- call `mergePair(...)` with `reason: 'auto'`, the score and the features

Everything in `80..94` simply stays `decision='pending'` — that **is** the review queue.
Everything below 80 stays `pending` too but is filtered out of the queue by the score floor;
record the counts of each band in `stats`.

**Run report.** One `ingest_runs` row is not right for this pass (its `source_key` CHECK admits
only the four data sources), so the resolve pass reports through `app.emit_event('businesses',
null-safe id, 'resolve', stats)` **plus** a printed summary. 🔴 If a persisted resolve-run row is
wanted later it is a new table with its own migration — do **not** widen
`ir_source_key_known` here, because `/sources` renders exactly four rows (D-17) and a fifth
would change that contract. State this choice in the SUMMARY.

`--dry-run` runs stages 1–4 and prints the band counts without merging anything.

🔴 Drizzle traps: bind `toISOString()` with `::timestamptz`; a JS array in a `sql` template
becomes N placeholders; a `timestamptz` read back is a string.

| Boundary | Description |

| desk resolve pass → `businesses` / `business_merges` | An owner connection performs ~10,000 merges |
| one org's candidates → another's | Every stage joins `businesses` to `businesses` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-01 | Tampering | `--org` | mitigate | Required and explicit; `resolveEtlOrg` throws rather than defaulting to "the only org" |
| T-3-15 | Elevation of privilege | ETL org context | mitigate | `resolveEtlOrg` installs a transaction-LOCAL `request.jwt.claims` carrying `{o:{id}}` only — no `sub`, no `o.rol`, no `set role` — so `app.record_merge` and `app.emit_event` resolve an org while the pass stays attributed `etl:resolve`. Stage 0 asserts `app.current_org_id()` is non-null before the pass does any work |
| T-3-12 | Denial of service | block explosion | mitigate | `MAX_BLOCK_PAIRS = 500`, the skip recorded in `stats.skipped_blocks`; B2 is never run ungated; B3 is bounded to five per left row |
| T-3-08 | Repudiation | auto-merge attribution | mitigate | Every merge goes through `app.record_merge`, which reads the actor itself; the pass sets `app.actor_id = 'etl:resolve'` so an auto-merge is attributable and distinguishable from a reviewed one |
| T-3-09 | Information disclosure | cross-org merge | mitigate | Every statement is bound to one `org_id`; `the pass is org-scoped` is the standing proof with two seeded orgs |
| T-3-02 | Repudiation | `merge_candidates.decision` | mitigate | The pass writes `merged` through the definer, never by a direct update from a session role |
</threat_model>
