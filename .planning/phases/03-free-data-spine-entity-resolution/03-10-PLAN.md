<objective>
Ship candidate generation: the three measured blocking shapes, the 25 km hard rule, the
block-size cap, and D-11 chain detection.

Purpose: all-pairs is **1,988,940,032** cross-source comparisons (34,928 Comptroller × 56,944
Overture) — 🔴 forty times STACK.md's "49 M" estimate — plus 1.62 billion intra-Overture. The
blocker reduces that to **29,701** distinct candidate pairs, a 66,970× reduction, in a ~2-minute
desk pass.

🔴 **The trap that wastes a day: the obvious join does not use the GIN index.**

```sql
-- NEVER WRITE THIS. Measured: 269,647 ms.
select … from ov join cm on ov.zip5 = cm.zip5 and ov.name_norm % cm.name_norm;
```

`EXPLAIN (ANALYZE, BUFFERS)` shows the planner picking the ZIP btree and applying `%` as a
post-index `Filter` — 85 million `similarity()` evaluations. The GIN trigram index cannot be
the driver when the probe value is a correlated column of the outer relation. The
`cross join lateral … order by <-> … limit 5` form makes the GIN index the driver (3.3 ms per
probe, `Bitmap Index Scan on businesses_name_trgm`, 43 buffers) and completes the full pass in
**101,807 ms**.

Output: `src/lib/resolve/block.ts`, `src/lib/resolve/chain.ts`, the grep gate and two DB tests.
</objective>

**B3 — the GIN lateral trigram top-5 within `postal`** (primary):

```sql
insert into merge_candidates (org_id, left_id, right_id, block_key, block_size, score, features, decision)
select $1, least(c.id, k.id), greatest(c.id, k.id), 'trgm_zip', null, 0, '{}'::jsonb, 'pending'
from businesses c
cross join lateral (
  select o.id
  from businesses o
  where o.org_id = c.org_id
    and o.id <> c.id
    and o.postal = c.postal
    and o.name_norm % c.name_norm
  order by o.name_norm <-> c.name_norm
  limit 5
) k
where c.org_id = $1 and c.name_norm is not null and c.postal is not null
  and c.merged_into_id is null
on conflict (org_id, left_id, right_id) do nothing;
```

🔴 `least`/`greatest` is what satisfies the `mc_pair_ordered` CHECK and stops one unordered pair
becoming two rows. 🔴 `merged_into_id is null` on both sides: a merged-away row is not a
candidate.

**The block-size cap.** `export const MAX_BLOCK_PAIRS = 500;`. Every block emits `block_key` and
`block_size`; a block whose size would exceed 500 pairs is **refused and recorded** in the run
report's `stats.skipped_blocks`, never silently truncated — a silently truncated block is how a
whole mall disappears from the spine (T-3-12).

**The 25 km hard rule (D-10)** — measured 303 ms over 332,738 pairs:

```sql
update merge_candidates mc
   set decision = 'distinct',
       features = mc.features || jsonb_build_object('distance_m', d.m, 'rule', 'over_25km')
  from businesses a, businesses b,
       lateral (select app.distance_m(a.lat, a.lng, b.lat, b.lng) as m) d
 where mc.org_id = $1 and mc.decision = 'pending'
   and a.id = mc.left_id and b.id = mc.right_id
   and a.lat is not null and b.lat is not null
   and d.m > 25000;
```

`src/lib/resolve/chain.ts` — D-11: **a flag, never a merge.**

```sql
with chains as (
  select name_norm, count(*) as n
  from businesses
  where org_id = $1 and name_norm is not null and merged_into_id is null
  group by name_norm
  having count(*) >= 3
)
update businesses b
   set chain_key = c.name_norm
  from chains c
 where b.org_id = $1 and b.name_norm = c.name_norm and b.merged_into_id is null;
```

🔴 `chain_key` **is the `name_norm` itself**, not a synthetic id: it is stable across runs, it is
what the badge's count groups on, and it is directly indexable. It carries **no provenance
pair** — it is derived, not sourced.

Measured, and worth stating in the header: **1,025** Overture names with ≥3 members covering
**9,782 rows (17.2 %)**, and **444** Comptroller names covering **2,091 rows (6.0 %)**. One in
six Overture rows will carry a chain flag, so ~17 % of the Overture spine is excluded from
auto-merge by this rule alone. The review queue shows the flag (`Chain · {n} in Texas`) and the
count belongs in the run report's `stats`.

⚠ D-11 says "across Texas" but this phase's spine is four counties, so a national chain with two
RGV outlets and 400 elsewhere would not be flagged. The statewide name-frequency request that
closes this properly is **03-12's** task (one extra Socrata request); `chainDetectionSql` takes
an optional statewide-frequency table name so it can consume it when present, and the badge copy
