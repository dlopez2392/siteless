The weight table, verbatim from 03-RESEARCH § The weight table — every feature emits its own
integer into `features` and the raw score is their clamped sum:

| Feature | Value | Range | Counts as an independent signal when |
|---|---|---|---|
| `name` | `Math.round(45 * clamp((nameSim - 0.40) / 0.60, 0, 1))` | 0…45 | `nameSim >= 0.85` |
| `phone` | 30 when both `phoneE164` present, equal, and **both `phoneBlockable`** | 0 or 30 | `=== 30` |
| `address` | 30 when `streetNum` + `streetNorm` + `postal` all equal; 15 when `streetNum` + `postal`; 5 when `postal` only; else 0 | 0…30 | `=== 30` |
| `distance` | 15 (≤100 m) / 10 (≤500 m) / 4 (≤2 km) / 0 (≤25 km) — both locations known **and neither side `census_non_exact`** | 0…15 | `distanceM <= 100` |
| `cluster` | `+5` same cluster · `0` either unmapped · **`-10` different cluster** | −10…+5 | never |

Distance uses the same haversine constant as `app.distance_m()` — earth radius
**6371000.0 m**, `2 * asin(sqrt(...))`. Both sides of the system must agree on the metre.

The structural rules, applied in this exact order, **each a separate named clause with a
one-test blast radius** (this, not the arithmetic, is what a test pins):

```
R1  both locations known AND distanceM > 25000   -> { decision:'distinct', score:0, rule:'over_25km' }   (D-10, M13)
R2  chainKey set on either side                  -> s = min(s, 94)                                       (D-11)
R3  phone signal AND a.postal === b.postal AND nameSim >= 0.60
        -> signals = max(signals, 2); s = max(s, 95); features.rule = 'phone_locality_name'              (D-07)
R4  phone signal AND a.postal === b.postal AND nameSim <  0.60
        -> s = clamp(s, 80, 94); features.rule = 'phone_locality_review'                                 (D-07)
R5  signals < 2                                  -> s = min(s, 94)                                       (D-09, M14)
R6  geoGate NOT satisfied                        -> s = min(s, 94)                                       (D-09/D-10, M15)
        geoGate := distanceM !== null && distanceM <= 500

band: >= 95 'merge' · 80–94 'review' · < 80 'ignore' · R1 short-circuits to 'distinct'
```

```ts
/** Crockford base32: 32 symbols, no I, L, O or U — the four that get misread aloud. */
const CROCKFORD = '0123456789ABCDEFGHJKMNPQRSTVWXYZ';

/** The shape the database CHECK also enforces. Kept here so the generator and the constraint
 *  cannot drift; `tests/db/external-key.test.ts` asserts the constraint separately. */
export const EXTERNAL_KEY_PATTERN = /^SL-[0-9A-HJKMNP-TV-Z]{6}$/;

export function newExternalKey(): string {
  const bytes = crypto.getRandomValues(new Uint8Array(6));
  return 'SL-' + Array.from(bytes, (b) => CROCKFORD[b % 32]).join('');
}
```

🔴 `crypto.getRandomValues`, never `Math.random` (ASVS V6). 🔴 `b % 32` over a uniform byte is
**exactly** uniform here because 256 = 8 × 32 — state that in a comment, because a 36-symbol
alphabet would not be and a reviewer will check.

🔴 **Six characters, not five.** D-19 permits 5–6; at RGV scale (92,000 pre-merge keys) a
5-character namespace of 33,554,432 gives `n²/2N = 126` — collisions are a certainty, ~126
expected. Six gives 1,073,741,824 slots, `n²/2N = 3.9`, ~4 expected over the whole RGV spine,
and the insert path retries on conflict. Record that arithmetic in the module header.

🔴 The key is **display-only**: never a foreign key, never a route parameter, never a query
key (UI-SPEC Executor Rule 18). Say so in the header.
