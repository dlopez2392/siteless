<objective>
Ship the committed `basic_category` → cluster mapping and load it through the existing seed
gate as reference rows.

Purpose: D-02 tags every source record with a cluster where its NAICS code falls in a seeded
range (Comptroller) **or** its `basic_category` maps to one (Overture). This is the Overture
half. **Unmapped rows stay in the spine and never enter the lead funnel** — so an unmapped
category must be *reported*, never guessed; a record that exists but is invisible is how a data
bug survives a quarter.

release (`2026-09-23.0`), and the roadmap and D-04 both require `basic_category`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tenant session → `overture_category_map` built-ins | Reference rows are `org_id IS NULL` and must be readable but not writable by any tenant |
| seed file → database | A committed JSON becomes reference rows via the owner connection |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-07 | Tampering | `overture_category_map` | mitigate | `referencePolicies()` — all three write policies require `org_id is not null and org_id = (select app.current_org_id())`, so a built-in is unreachable from a tenant. Proven by the zero-rows / `42501` split in `reference-rows.test.ts` |
| T-3-03 | Tampering | `scripts/seed.ts` | mitigate | Every value is a bound parameter; the JSON is a committed repo file, not a fetched payload, and three unit tests pin its shape before it reaches the database |
| T-3-01 | Tampering | seed target | mitigate | `resolveSeedTarget` gates `--target=test|prod` explicitly; `db:seed:prod` is a separate script and a human checkpoint (03-21) |
</threat_model>
