<objective>
Load the committed seed data into the reference tables idempotently, and prove the three properties that make a built-in a built-in and a version a version: a re-run changes nothing, a tenant cannot touch a built-in, and a past run still points at the version that produced it.

Purpose: SRCH-02 says the clusters, the city list and the counties "ship as seed data" — the test of that claim is that `db:seed` twice produces the same row counts, which is only true because of `UNIQUE NULLS NOT DISTINCT`. SRCH-03's "past runs keep pointing at the version that produced them" is an FK and a revoked grant, and this plan is where both are watched failing first.
Output: `scripts/seed.ts`, a CI step that seeds before `test:db`, and three DB test files.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| seed loader (owner) -> reference tables | The loader bypasses RLS by running as the owner; a bug there writes rows every tenant reads |
| tenant session -> built-in reference rows | Shared across all tenants; a mutation would be a cross-tenant mutation |
| tenant session -> its own version history | Editing a past version rewrites what a completed run means |
| `--target=test` -> the production Supabase project | A seed pointed at production writes reference rows outside the migration authority |
