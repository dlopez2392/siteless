**`src/lib/estimate/expand-cells.ts`** — pure, no I/O. `expandCells(spec: PresetSpec, seed: SeedTables): Cell[]` where a `Cell` is `{ clusterKey, unitKind: 'city'|'county'|'radius', unitId, expectedOutlets }`. Cells are `|clusters| x |geography units|`.
  - `counties`: `expectedOutlets = outletCounts[scope 'county'][countyFips][clusterKey]`, read straight from the seed.
  - `cities` (D-09, apportion from the county count): `expectedOutlets = Math.round(countyClusterOutlets * city.outletCount / county.outletCount)`. Worked example that becomes a pinned test: McAllen x home_services = `round(969 * 5985 / 21062) = 275`.
  - `radius`: ONE cell per cluster over the geocoded county, `expectedOutlets = Math.round(countyClusterOutlets * Math.min(1, (radiusMiles / RADIUS_REFERENCE_MILES) ** 2))`. Worked example: McAllen centre, Hidalgo, 10 miles, home_services = `round(969 * 0.16) = 155`. This approximation is documented in the assumptions drawer; it changes the expected-result count only, never the request count, because a radius is one geography unit either way.

**`src/lib/geocode/census.ts`** — the ONLY external HTTP call in this phase. `import 'server-only'` on line 1, exactly as `src/env.ts` and `src/db/with-org.ts` do.

```
const CENSUS_HOST = 'https://geocoding.geo.census.gov';
const CENSUS_PATH = '/geocoder/geographies/onelineaddress';
export type GeocodeResult =
  | { ok: true; lat: number; lng: number; countyFips: string; countyName: string; matchedAddress: string }
  | { ok: false; reason: 'no_match' | 'not_texas' | 'unreachable' | 'bad_shape' };
export async function geocodeAddress(address: string): Promise<GeocodeResult>;
```

Request: `benchmark=Public_AR_Current`, `vintage=Current_Current`, `format=json`, `layers=Counties`, and the caller's string as the `address` query parameter **and nowhere else**. 🔴 T-2-13: the host and path are hard-coded constants; the address is length-bounded (3 to 200 characters) and charset-bounded by a zod schema before the URL is built; the response is parsed, never evaluated. No user input ever reaches the host, the path or a header.
🔴 `layers=Counties` is load-bearing for cost of a different kind: the default response carries 11 geography layers at 5,125 bytes, this one is 1,154 bytes and still carries `COUNTY`, `GEOID`, `NAME` and `STATE`.
Timeout: `AbortSignal.timeout(8000)` — measured latency is 138 to 550 ms, so eight seconds is generous and bounded.

Response handling, all four outcomes:
  - 🔴 **The failure mode is HTTP 200.** Every failing case returns `200` with `addressMatches: []`. A status check is NOT a success check. `addressMatches.length === 0` is the documented no-match outcome, not a parse error, and returns `{ ok: false, reason: 'no_match' }`.
  - zod parse, exactly RESEARCH's verified shape: `result.addressMatches[]` each with `matchedAddress`, `coordinates: { x, y }` — 🔴 **`x` is LONGITUDE and `y` is LATITUDE**, not `(lat, lng)` — and `geographies.Counties[]` each with `GEOID`, `COUNTY`, `NAME`, `STATE`. A parse failure returns `{ ok: false, reason: 'bad_shape' }`.
  - `STATE !== '48'` returns `{ ok: false, reason: 'not_texas' }` — DATA-SOURCES records that a naive RGV bounding box is 42% Mexico, and the Texas-side clip is free here.
  - A non-2xx status or a thrown fetch returns `{ ok: false, reason: 'unreachable' }`.
Persist only `{lat, lng, countyFips, countyName, matchedAddress}` on the version row — never the raw payload.
🔴 A bad ZIP is silently CORRECTED by the service (`78501` is returned for a query that said `99999`), so the `matchedAddress` the caller shows must be the one the service returned, not the one the user typed. UI-SPEC's geocode-result copy (`Matched: {address} - {county} County`) depends on that.
